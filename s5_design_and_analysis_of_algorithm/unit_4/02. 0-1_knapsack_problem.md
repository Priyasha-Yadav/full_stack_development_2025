# 0/1 Knapsack Problem
## 1. What is the "0/1 Knapsack Problem"?

### 1.1 Simple Meaning

The **0/1 Knapsack Problem** asks: *you have a bag that can carry only a limited weight, and a set of items, each with a **weight** and a **value**. Which items should you put in the bag to get the **largest total value** without going over the weight limit?*

Every item is either taken **whole** or **left behind** -- you cannot take half of an item, and you cannot take the same item twice. That is where the name "0/1" comes from: for each item the choice is `0` (leave it) or `1` (take it).

It sounds easy, but a natural first idea -- "always pick the item with the best value for its weight" -- **does not always work**. This note shows why, and then solves the problem correctly with **Dynamic Programming** (see the Introduction to Dynamic Programming note). The table-filling idea is very close to the one in the Making Change Problem note, with one important difference that Section 5 points out.

### 1.2 Everyday Analogy

Imagine a **hiker packing a backpack** that can carry at most **7 kg**. On the bed lie four items. Each has a weight in kg and a "usefulness" score (its value). Everything cannot fit, so the hiker must choose. Items cannot be cut into pieces (a tent is either packed or not), and there is only one of each. The hiker wants the **highest total usefulness** that still fits in the 7 kg limit.

### 1.3 The Problem Statement

| Part | Meaning |
| :-- | :-- |
| **Input** | `n` items with weights `w1, w2, ..., wn` and values `v1, v2, ..., vn`, and a bag capacity `W` (all whole numbers, every weight at least 1) |
| **Assumption** | Each item can be used **at most once** (take it whole or leave it) |
| **Goal** | Make the **total value as large as possible**, with the **total weight at most `W`** |
| **Output** | The largest total value, and which items give it |

Notice one difference from the Making Change Problem: here the total weight only has to be **at most** `W`, not exactly `W`. Leaving some room in the bag is allowed. For that reason the answer always exists (taking nothing gives value `0`), so there is no "impossible" case.

### 1.4 Our Running Example

**Capacity:** `W = 7`

| Item | Weight | Value |
| :-: | :-: | :-: |
| **1** | 1 | 1 |
| **2** | 3 | 4 |
| **3** | 4 | 5 |
| **4** | 5 | 7 |

With 4 items there are only `2 x 2 x 2 x 2 = 16` ways to choose (each item is taken or left). Here is **every** way. The "Choice" column writes `1` for taken and `0` for left, in the order of items 1, 2, 3, 4:

| # | Choice | Items Taken | Total Weight | Total Value | Fits in 7? |
| :-: | :-: | :-- | :-: | :-: | :-: |
| 1 | `0000` | none | 0 | 0 | Yes |
| 2 | `1000` | 1 | 1 | 1 | Yes |
| 3 | `0100` | 2 | 3 | 4 | Yes |
| 4 | `0010` | 3 | 4 | 5 | Yes |
| 5 | `0001` | 4 | 5 | 7 | Yes |
| 6 | `1100` | 1, 2 | 4 | 5 | Yes |
| 7 | `1010` | 1, 3 | 5 | 6 | Yes |
| 8 | `1001` | 1, 4 | 6 | 8 | Yes |
| 9 | `0110` | 2, 3 | 7 | **9 (best)** | Yes |
| 10 | `0101` | 2, 4 | 8 | 11 | **No** |
| 11 | `0011` | 3, 4 | 9 | 12 | **No** |
| 12 | `1110` | 1, 2, 3 | 8 | 10 | **No** |
| 13 | `1101` | 1, 2, 4 | 9 | 12 | **No** |
| 14 | `1011` | 1, 3, 4 | 10 | 13 | **No** |
| 15 | `0111` | 2, 3, 4 | 12 | 16 | **No** |
| 16 | `1111` | 1, 2, 3, 4 | 13 | 17 | **No** |

Only **9 of the 16** choices fit in the bag. The heavier choices have bigger values, but they do not fit, so they do not count. The best choice that fits is **items 2 and 3** (weight `3 + 4 = 7`, value `4 + 5 = 9`).

So the correct answer is **value 9**. For big inputs, listing every way is impossible, because the number of ways doubles with each extra item:

| Items `n` | Ways to Choose (`2^n`) |
| :-: | :-: |
| 4 | 16 |
| 10 | 1,024 |
| 20 | 1,048,576 |
| 30 | 1,073,741,824 |

We need a smart method. The rest of this note builds one, using this same example throughout.

### 1.5 Why Is It Called "0/1"?

For every item there are only two choices. Our best answer `0110` looks like this:

```
Item        1      2      3      4
Choice     [0]    [1]    [1]    [0]      0 = leave it,  1 = take it
            |      |      |      |
          left   TAKEN  TAKEN   left     -> items 2 and 3, value 4 + 5 = 9
```

An item cannot be cut (so no "half of item 4") and cannot be used twice (so no "item 2 two times"). Section 5 compares this with the versions of the problem where those rules change.

### 1.6 Where Is It Used?

| Application | What the Knapsack Idea Does |
| :-- | :-- |
| **Budget Planning** | Choose projects or purchases (weight = cost, value = benefit) that fit in a fixed budget |
| **Cargo and Luggage Loading** | Choose which packages to load so the value is highest without passing the weight limit |
| **Investment Selection** | Choose which investments to buy with a limited amount of money |
| **Study or Exam Planning** | Choose topics or questions (weight = time needed, value = marks) that fit in the available time |
| **Computer Resource Planning** | Choose which jobs to run when memory or time is limited |

## 2. First Idea -- The Greedy Method

### 2.1 The Greedy Rules

A **greedy** method makes the choice that **looks best right now** and never changes its mind. For knapsack, there are three natural rules for "looks best". Take the items in this order, and put each one in the bag **if it still fits**:

| Rule | Order in Which Items Are Tried |
| :-- | :-- |
| **A. Highest value first** | Biggest value to smallest value |
| **B. Lightest first** | Smallest weight to largest weight |
| **C. Best value per kg first** | Biggest `value / weight` to smallest |

Rule C looks the cleverest, because it asks "which item gives the most value for each kg of space it uses?". The value per kg of our items are:

| Item | Weight | Value | Value per kg (`v / w`) |
| :-: | :-: | :-: | :-: |
| 1 | 1 | 1 | 1.00 |
| 2 | 3 | 4 | 1.33 |
| 3 | 4 | 5 | 1.25 |
| 4 | 5 | 7 | **1.40** (best) |

So under Rule C the order is **item 4, item 2, item 3, item 1**.

### 2.2 Greedy Step by Step for Capacity 7 (Rule C)

| Step | Item Tried | Weight | Room Left Before | Does It Fit? | Action | Room Left After | Value So Far |
| :-: | :-: | :-: | :-: | :-: | :-- | :-: | :-: |
| 1 | 4 | 5 | 7 | Yes | Take it | 2 | 7 |
| 2 | 2 | 3 | 2 | No (3 > 2) | Skip it | 2 | 7 |
| 3 | 3 | 4 | 2 | No (4 > 2) | Skip it | 2 | 7 |
| 4 | 1 | 1 | 2 | Yes | Take it | 1 | 8 |

Greedy finishes with **items 4 and 1**: weight `5 + 1 = 6`, value `7 + 1 = 8`. But we saw in Section 1.4 that items 2 and 3 give **value 9**. So greedy gave a **wrong (not the best)** answer.

### 2.3 All Three Rules Compared

| Rule | Order Tried | Items Taken | Total Weight | Total Value |
| :-- | :-: | :-: | :-: | :-: |
| **A. Highest value first** | 4, 3, 2, 1 | 4, 1 | 6 | 8 |
| **B. Lightest first** | 1, 2, 3, 4 | 1, 2 | 4 | 5 |
| **C. Best value per kg** | 4, 2, 3, 1 | 4, 1 | 6 | 8 |
| **Best possible (Section 1.4)** | -- | 2, 3 | 7 | **9** |

**None of the three rules finds the best answer.**

### 2.4 Greedy and the Best Answer, Drawn to Scale

Each item is drawn as a box whose length is proportional to its weight (each kg is 4 characters wide). The bag holds 7 kg:

```
            0   1   2   3   4   5   6   7
            |   |   |   |   |   |   |   |
Greedy   :  [      item 4      ][i1]....     value 7 + 1 = 8
Best     :  [  item 2  ][    item 3    ]     value 4 + 5 = 9

            [i1] = item 1 (1 kg)        .... = 1 kg of the bag left empty
```

The best answer fills the bag **exactly** (all 7 kg are used), while greedy leaves 1 kg unused.

### 2.5 Greedy Code

```cpp
#include <iostream>
using namespace std;

// Returns true if item a should come BEFORE item b for the chosen rule.
// rule 1 = highest value first, rule 2 = lightest first, rule 3 = best value/weight ratio first
bool comesFirst(int w[], int v[], int a, int b, int rule) {
    if (rule == 1) return v[a] > v[b];
    if (rule == 2) return w[a] < w[b];
    return v[a] * w[b] > v[b] * w[a];      // same as v[a]/w[a] > v[b]/w[b], without decimals
}

void greedy(int w[], int v[], int n, int cap, int rule, const char* name) {
    int order[10];
    for (int i = 0; i < n; i++) order[i] = i;

    // Sort the item numbers by the rule (simple bubble sort)
    for (int i = 0; i < n - 1; i++)
        for (int j = 0; j < n - 1 - i; j++)
            if (comesFirst(w, v, order[j + 1], order[j], rule)) {
                int temp = order[j];
                order[j] = order[j + 1];
                order[j + 1] = temp;
            }

    int left = cap, total = 0, used = 0;
    cout << name << " -> items: ";
    for (int k = 0; k < n; k++) {
        int i = order[k];
        if (w[i] <= left) {                // it fits: take the WHOLE item, never undo
            cout << i + 1 << " ";
            left = left - w[i];
            used = used + w[i];
            total = total + v[i];
        }
    }
    cout << "| weight = " << used << ", value = " << total << endl;
}

int main() {
    int w[] = {1, 3, 4, 5};
    int v[] = {1, 4, 5, 7};

    greedy(w, v, 4, 7, 1, "Highest value first   ");
    greedy(w, v, 4, 7, 2, "Lightest first        ");
    greedy(w, v, 4, 7, 3, "Best value/weight     ");

    return 0;
}
```

**Verified Output:**
```
Highest value first    -> items: 4 1 | weight = 6, value = 8
Lightest first         -> items: 1 2 | weight = 4, value = 5
Best value/weight      -> items: 4 1 | weight = 6, value = 8
```

The three lines match the first three rows of the table in Section 2.3, and the last line (Rule C) matches the step-by-step trace in Section 2.2. Notice that the **best** answer, value `9`, is never produced by any of the three greedy rules.

### 2.6 Why Greedy Fails

Greedy grabbed **item 4** because it had the best value per kg. That left only 2 kg of room, and the only item that fits in 2 kg is item 1 (value 1). The best answer **avoids item 4 altogether**, and uses the space perfectly with items 2 and 3. Greedy **cannot go back and undo** its first choice, so it never discovers this.

The real problem is that items are **all or nothing**. A great-looking item can leave a gap that nothing else can fill properly.

### 2.7 When Does Greedy Work?

Greedy **does** give the best answer when items **can be cut into pieces** (called the **Fractional Knapsack**). Then the leftover gap can always be filled with a piece of the next-best item. For our items with capacity 7:

| Step | Item | Part Taken | Room Left After | Value Added |
| :-: | :-: | :-- | :-: | :-: |
| 1 | 4 | all 5 kg | 2 | 7 |
| 2 | 2 | only 2 of its 3 kg (two thirds) | 0 | `2/3 x 4` = about 2.67 |

The total is about **9.67**, which is **more than 9**. That is only possible because we were allowed to cut item 2 -- in the 0/1 problem we may not, so the best we can do is 9.

> **Important:** greedy is fine for the **Fractional** version, but for the **0/1** version it cannot be trusted. We need a method that is **always correct**.

## 3. Thinking Recursively -- Finding the Recurrence

### 3.1 The Key Idea

Look at the **last item** (item `n`). In a best bag there are only two possibilities:

| Case | What It Means | What Is Left to Solve |
| :-: | :-- | :-- |
| **1. Item `n` is NOT in the bag** | Leave it out | The best bag using the first `n - 1` items, with the **same** capacity |
| **2. Item `n` IS in the bag** | Put it in (only possible if `wn <= W`) | The value `vn`, plus the best bag using the first `n - 1` items, with the **smaller** capacity `W - wn` |

In Case 2 the other items must be the **best possible** for the smaller capacity -- otherwise we could swap in a better set for them and improve the whole bag. This is the **principle of optimality** from the Dynamic Programming note: *a best answer is built from best answers to smaller problems.*

We do not know which case is the winner, so we **try both** and keep the better one.

### 3.2 The Recurrence

Let `f(i, c)` = the largest value we can get using **only the first `i` items** when the bag can carry `c`.

```
f(0, c) = 0                                   (no items: nothing to gain)
f(i, 0) = 0                                   (no room: nothing fits)

f(i, c) = f(i-1, c)                           if wi > c    (item i is too heavy: must skip it)
f(i, c) = max( f(i-1, c) , vi + f(i-1, c - wi) )   if wi <= c   (skip it, or take it)
```

The answer to the whole problem is `f(n, W)`. Notice that in the "take" case the second part is `f(i-1, ...)` -- the **first `i - 1` items**, not `i` items -- because item `i` has just been used and cannot be used again.

### 3.3 Working It Out by Hand

We want `f(4, 7)`. Using the recurrence, here are all the calls that are not trivial, from the smallest to the answer. The items are `1 = (w 1, v 1)`, `2 = (w 3, v 4)`, `3 = (w 4, v 5)`, `4 = (w 5, v 7)`:

| Call | Item `i` | Fits? | Skip: `f(i-1, c)` | Take: `vi + f(i-1, c-wi)` | Best |
| :-: | :-: | :-: | :-: | :-: | :-: |
| `f(1, 7)` | 1 | Yes | `f(0,7)` = 0 | `1 + f(0,6)` = 1 | **1** |
| `f(1, 4)` | 1 | Yes | `f(0,4)` = 0 | `1 + f(0,3)` = 1 | **1** |
| `f(1, 3)` | 1 | Yes | `f(0,3)` = 0 | `1 + f(0,2)` = 1 | **1** |
| `f(1, 2)` | 1 | Yes | `f(0,2)` = 0 | `1 + f(0,1)` = 1 | **1** |
| `f(2, 7)` | 2 | Yes (3 <= 7) | `f(1,7)` = 1 | `4 + f(1,4)` = 5 | **5** |
| `f(2, 3)` | 2 | Yes (3 <= 3) | `f(1,3)` = 1 | `4 + f(1,0)` = 4 | **4** |
| `f(2, 2)` | 2 | No (3 > 2) | `f(1,2)` = 1 | -- | **1** |
| `f(3, 7)` | 3 | Yes (4 <= 7) | `f(2,7)` = 5 | `5 + f(2,3)` = 9 | **9** |
| `f(3, 2)` | 3 | No (4 > 2) | `f(2,2)` = 1 | -- | **1** |
| `f(4, 7)` | 4 | Yes (5 <= 7) | `f(3,7)` = 9 | `7 + f(3,2)` = 8 | **9** |

So `f(4, 7) = 9`, as expected. Notice the last row: **taking item 4 gives only 8**, because it leaves just 2 kg of room. **Skipping item 4 gives 9.** That is exactly why greedy was wrong.

### 3.4 The Recurrence as Plain Recursion

We can turn the recurrence straight into a recursive function. It tries both choices and keeps the larger result:

```cpp
#include <iostream>
using namespace std;

long long callCount = 0;   // counts how many times knap() is called

// Best value using the first i items when the bag can still carry cap
int knap(int w[], int v[], int i, int cap) {
    callCount++;

    if (i == 0 || cap == 0)                    // base case: no items left, or no room left
        return 0;

    if (w[i - 1] > cap)                        // item i is too heavy: we must skip it
        return knap(w, v, i - 1, cap);

    int skip = knap(w, v, i - 1, cap);                       // option 1: leave item i out
    int take = v[i - 1] + knap(w, v, i - 1, cap - w[i - 1]); // option 2: put item i in
    return (skip > take) ? skip : take;
}

int main() {
    int w[] = {1, 3, 4, 5};
    int v[] = {1, 4, 5, 7};
    cout << "Items 1-4, capacity 7: best value = " << knap(w, v, 4, 7)
         << "   calls = " << callCount << endl;
    cout << endl;

    // Growth test: repeat the same 4 items again and again; capacity = number of items
    int bw[30], bv[30];
    for (int k = 0; k < 30; k++) {
        bw[k] = w[k % 4];
        bv[k] = v[k % 4];
    }
    int sizes[] = {4, 8, 12, 16, 20, 24};
    for (int s = 0; s < 6; s++) {
        int n = sizes[s];
        callCount = 0;
        int result = knap(bw, bv, n, n);
        cout << "n = " << n << " items, capacity " << n << ": best value = " << result
             << "   calls = " << callCount << endl;
    }
    return 0;
}
```

**Verified Output:**
```
Items 1-4, capacity 7: best value = 9   calls = 19

n = 4 items, capacity 4: best value = 5   calls = 10
n = 8 items, capacity 8: best value = 11   calls = 114
n = 12 items, capacity 12: best value = 16   calls = 1285
n = 16 items, capacity 16: best value = 22   calls = 14689
n = 20 items, capacity 20: best value = 28   calls = 169073
n = 24 items, capacity 24: best value = 33   calls = 1961491
```

The first line is our running example: the answer `9`, found with **19 calls**. The other lines repeat the same four items again and again (items 1, 2, 3, 4, 1, 2, 3, 4, ...) with the capacity equal to the number of items, to see how the work grows. The answers are right, but the `calls` column grows very fast. Section 3.5 shows the 19 calls for our example, and Section 3.6 explains the growth.

### 3.5 The Recursion Tree for f(4, 7)

Here is every call made while computing `f(4, 7)`. A child is drawn under its parent. The first child is the **skip** call `f(i-1, c)`, the second child (when it exists) is the **take** call `f(i-1, c-wi)`. A call marked `*` repeats a subproblem that **already appeared earlier** in the tree:

```
f(4,7)
+-- f(3,7)                        skip item 4
|   +-- f(2,7)                    skip item 3
|   |   +-- f(1,7)                skip item 2
|   |   |   +-- f(0,7)            skip item 1   (no items left: 0)
|   |   |   +-- f(0,6)            take item 1   (no items left: 0)
|   |   +-- f(1,4)                take item 2   (7 - 3 = 4 left)
|   |       +-- f(0,4)
|   |       +-- f(0,3)
|   +-- f(2,3)                    take item 3   (7 - 4 = 3 left)
|       +-- f(1,3)                skip item 2
|       |   +-- f(0,3)   * repeat
|       |   +-- f(0,2)
|       +-- f(1,0)                take item 2   (3 - 3 = 0 left: stop)
+-- f(3,2)                        take item 4   (7 - 5 = 2 left)
    +-- f(2,2)                    item 3 is too heavy: only "skip"
        +-- f(1,2)                item 2 is too heavy: only "skip"
            +-- f(0,2)   * repeat
            +-- f(0,1)
```

`* repeat` = this exact `(items, capacity)` pair was already solved earlier in the tree.

| Kind of Call | How Many |
| :-- | :-: |
| Calls that make a real choice (rows of the table in Section 3.3) | 10 |
| Calls that stop at once (`f(0, c)` or `f(i, 0)`) | 9 |
| **Total calls** | **19** |
| Different `(i, c)` pairs among them | 17 |

There are 17 different subproblems and 19 calls, so only **2 calls are pure repetition**, and both are the trivial `f(0, c)` calls. This matches exactly the `calls = 19` printed in Section 3.4. In such a **tiny** example there is little repetition. The next section shows that this changes quickly as the problem grows.

### 3.6 How Bad Does It Get?

From the program run in Section 3.4 (the four items repeated again and again, capacity = number of items):

| Items `n` | Capacity `W` | Calls by Plain Recursion | Table Cells `(n+1)(W+1)` | Note |
| :-: | :-: | :-: | :-: | :-- |
| 4 | 4 | 10 | 25 | Run above |
| 8 | 8 | 114 | 81 | Run above |
| 12 | 12 | 1,285 | 169 | Run above |
| 16 | 16 | 14,689 | 289 | Run above |
| 20 | 20 | 169,073 | 441 | Run above |
| 24 | 24 | 1,961,491 | 625 | Run above |

Every 4 extra items make the number of calls roughly **11.5 times bigger**. That is **exponential growth**. Meanwhile the number of different `(i, c)` pairs -- the table cells -- grows only slowly. For very small inputs the recursion can even be cheaper (4 items: 10 calls against 25 cells), because it only visits the pairs it needs. From 8 items onward the table is cheaper, and by 12 items the gap is already huge (1,285 calls against 169 cells).

### 3.7 Why Can This Problem Be Solved with Dynamic Programming?

| # | Point | What We See in Knapsack | Why It Matters for DP |
| :-: | :-- | :-- | :-- |
| **1** | **Smaller subproblems of the same kind** | `f(i, c)` is built from `f(i-1, ...)` | We have a recurrence |
| **2** | **Optimal substructure** | A best bag for `(i, c)` contains a best bag for the smaller problem (Section 3.1) | It is safe to build answers from best smaller answers |
| **3** | **The subproblems overlap** | The same `(i, c)` pair is reached by different routes: for example "take item A, skip item B" and "skip A, take B" end in the same place when A and B weigh the same. In the growth test, 24 items needed 1,961,491 calls | Saving an answer avoids repeated work |
| **4** | **Only a few different subproblems** | At most `(n + 1)(W + 1)` different pairs, although there may be millions of calls | A small table can hold every answer |
| **5** | **A subproblem always has the same answer** | `f(2, 3)` is always `4` | Safe to save and reuse |
| **6** | **There is a natural order** | Row `i` needs only row `i - 1` | Fill the table row by row: 0, 1, 2, ... `n` |

**Conclusion:** 0/1 Knapsack has everything DP needs. The next section builds the table.

## 4. Dynamic Programming Solution -- The Table

### 4.1 The Table

We use the classic table that also lets us find **which items** were taken. Let the items be numbered `1, 2, ..., n`:

```
K[i][j] = the largest value we can get using ONLY the first i items,
          when the bag can carry j
```

- **Rows** `i = 0, 1, ..., n`: row `i` means "we are allowed to use the first `i` items".
- **Columns** `j = 0, 1, ..., W`: the capacity of the bag.
- The answer to the whole problem is the **bottom-right cell**, `K[n][W]`.

This is the recurrence `f(i, c)` of Section 3.2 written as a table: `K[i][j]` is simply `f(i, j)`.

### 4.2 The Five Steps Applied

| # | Step | For 0/1 Knapsack |
| :-: | :-- | :-- |
| **1** | Define the subproblem | `K[i][j]` = best value using the first `i` items with capacity `j` |
| **2** | Write the recurrence | Either leave item `i` out, or take it (Section 4.3) |
| **3** | Set the base cases | `K[0][j] = 0` for every `j`, and `K[i][0] = 0` for every `i` |
| **4** | Choose the order | Row by row from `i = 1`, and left to right inside a row |
| **5** | Find the final answer | `K[n][W]` |

### 4.3 The Rules for Filling a Cell

Let `wt` be the weight and `val` the value of item number `i`.

| Situation | Rule | Meaning |
| :-- | :-- | :-- |
| `j = 0` | `K[i][0] = 0` | No room, so nothing fits |
| `i = 0` | `K[0][j] = 0` | No items, so no value |
| `wt > j` | `K[i][j] = K[i-1][j]` | Item `i` is too heavy, so copy the cell above |
| `wt <= j` | `K[i][j] = max( K[i-1][j] , val + K[i-1][j-wt] )` | Pick the better of two options (below) |

```
                 column j - wt                 column j
                       |                           |
row i-1  :       K[i-1][j-wt]                  K[i-1][j]
                       |                           |
                       |  + val                    |  copy it as it is
                       |  (option 2: TAKE item i)  |  (option 1: LEAVE item i)
                       +-------------+-------------+
                                     |
                                     v
row i    :                        K[i][j]  = the larger of the two
```

- **Option 1 -- leave item `i` out:** the answer is the same as with only the first `i - 1` items, which is the cell **above**.
- **Option 2 -- take item `i`:** we gain `val`, and we have `j - wt` kg of room left for the other items. We look that up in the **row above** (`i - 1`), because item `i` has just been used and may **not** be used again.

> **Important:** both options read from row `i - 1`. In the Making Change note, the "use the coin" option read from the **same row** (`c[i][j-d]`), because a coin could be used again. That one difference is what separates "use as many times as you like" from "use at most once".

### 4.4 Worked Example -- Step by Step (items below, capacity 7)

Items: `1 = (w 1, v 1)`, `2 = (w 3, v 4)`, `3 = (w 4, v 5)`, `4 = (w 5, v 7)`.

**Row 0 (no items).** Nothing can be gained, and column 0 is always 0:

| `j` | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| :-- | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| **`K[0][j]`** | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

**Row 1 (item 1: weight 1, value 1).** Item 1 fits every capacity `j >= 1`, so `K[1][j] = max( K[0][j] , 1 + K[0][j-1] )`:

| `j` | Option 1: `K[0][j]` | Option 2: `1 + K[0][j-1]` | `K[1][j]` |
| :-: | :-: | :-: | :-: |
| 1 | 0 | 1 + 0 = 1 | **1** |
| 2 | 0 | 1 + 0 = 1 | **1** |
| 3 | 0 | 1 + 0 = 1 | **1** |
| 4 | 0 | 1 + 0 = 1 | **1** |
| 5 | 0 | 1 + 0 = 1 | **1** |
| 6 | 0 | 1 + 0 = 1 | **1** |
| 7 | 0 | 1 + 0 = 1 | **1** |

With only item 1 available, the best value is 1 whenever the bag can hold it. It cannot be taken twice, so the value never goes above 1.

**Row 2 (item 2: weight 3, value 4).** For `j = 0` to `2`, item 2 is too heavy, so we **copy the cell above**: `0, 1, 1`. For `j = 3` to `7`, `K[2][j] = max( K[1][j] , 4 + K[1][j-3] )`:

| `j` | Option 1: `K[1][j]` | Option 2: `4 + K[1][j-3]` | `K[2][j]` | Which Option Won |
| :-: | :-: | :-: | :-: | :-- |
| 3 | 1 | 4 + `K[1][0]` = 4 + 0 = 4 | **4** | Option 2: take item 2 |
| 4 | 1 | 4 + `K[1][1]` = 4 + 1 = 5 | **5** | Option 2: items 2 and 1 |
| 5 | 1 | 4 + `K[1][2]` = 4 + 1 = 5 | **5** | Option 2: items 2 and 1 |
| 6 | 1 | 4 + `K[1][3]` = 4 + 1 = 5 | **5** | Option 2: items 2 and 1 |
| 7 | 1 | 4 + `K[1][4]` = 4 + 1 = 5 | **5** | Option 2: items 2 and 1 |

The value stays at 5 for `j = 4` to `7` because only items 1 and 2 are available, and together they weigh just 4 kg.

**Row 3 (item 3: weight 4, value 5).** For `j = 0` to `3`, item 3 is too heavy, so we **copy the cell above**: `0, 1, 1, 4`. For `j = 4` to `7`, `K[3][j] = max( K[2][j] , 5 + K[2][j-4] )`:

| `j` | Option 1: `K[2][j]` | Option 2: `5 + K[2][j-4]` | `K[3][j]` | Which Option Won |
| :-: | :-: | :-: | :-: | :-- |
| 4 | 5 | 5 + `K[2][0]` = 5 + 0 = 5 | **5** | Tie (5 and 5): we keep Option 1, as Option 2 is not larger |
| 5 | 5 | 5 + `K[2][1]` = 5 + 1 = 6 | **6** | Option 2: items 3 and 1 |
| 6 | 5 | 5 + `K[2][2]` = 5 + 1 = 6 | **6** | Option 2: items 3 and 1 |
| 7 | 5 | 5 + `K[2][3]` = 5 + 4 = 9 | **9** | Option 2: items 3 and 2 |

At `j = 7` the table finds the best answer so far: item 3 (4 kg) plus the best way to use the remaining 3 kg on items 1 and 2, which is item 2 (value 4).

**Row 4 (item 4: weight 5, value 7).** For `j = 0` to `4`, item 4 is too heavy, so we **copy the cell above**: `0, 1, 1, 4, 5`. For `j = 5` to `7`, `K[4][j] = max( K[3][j] , 7 + K[3][j-5] )`:

| `j` | Option 1: `K[3][j]` | Option 2: `7 + K[3][j-5]` | `K[4][j]` | Which Option Won |
| :-: | :-: | :-: | :-: | :-- |
| 5 | 6 | 7 + `K[3][0]` = 7 + 0 = 7 | **7** | Option 2: item 4 alone |
| 6 | 6 | 7 + `K[3][1]` = 7 + 1 = 8 | **8** | Option 2: items 4 and 1 |
| 7 | 9 | 7 + `K[3][2]` = 7 + 1 = 8 | **9** | Option 1: item 4 does not help |

**Answer:** `K[4][7] = 9`, the largest value that fits in 7 kg. At `j = 7`, taking item 4 gives only 8, so the table keeps the 9 that was already there -- this is exactly the step where greedy went wrong.

### 4.5 The Finished Table

Here is the whole table. The cells in square brackets `[ ]` are the ones we will use in Section 4.6 to find the items:

```
              j=0   j=1   j=2   j=3   j=4   j=5   j=6   j=7
            +-----+-----+-----+-----+-----+-----+-----+-----+
no items    |  0  |  0  |  0  |  0  |  0  |  0  |  0  |  0  |
            +-----+-----+-----+-----+-----+-----+-----+-----+
item 1      |[ 0 ]|  1  |  1  |  1  |  1  |  1  |  1  |  1  |
            +-----+-----+-----+-----+-----+-----+-----+-----+
item 2      |  0  |  1  |  1  |[ 4 ]|  5  |  5  |  5  |  5  |
            +-----+-----+-----+-----+-----+-----+-----+-----+
item 3      |  0  |  1  |  1  |  4  |  5  |  6  |  6  |[ 9 ]|
            +-----+-----+-----+-----+-----+-----+-----+-----+
item 4      |  0  |  1  |  1  |  4  |  5  |  7  |  8  |[ 9 ]|
            +-----+-----+-----+-----+-----+-----+-----+-----+

            weights:  item 1 = 1,  item 2 = 3,  item 3 = 4,  item 4 = 5
```

The last row, `0 1 1 4 5 7 8 9`, gives the best answer for **every capacity from 0 up to 7**, not just for 7. For example, a bag of capacity 5 can hold value 7 (item 4 alone), and a bag of capacity 4 can hold value 5.

### 4.6 Finding Which Items Were Taken

The number `9` tells us the **best value**. To find **which** items, we walk back through the table, starting at the answer cell `K[4][7]`. In every row, from the last up to row 1, we compare the cell with the cell **above** it:

- If `K[i][j] = K[i-1][j]`, item `i` was **not needed**.
- Otherwise item `i` **was taken**: write it down and reduce `j` by its weight (`j` becomes `j - wt`).
- Either way, move **up** one row. Stop after row 1.

| Step | Position `(i, j)` | `K[i][j]` vs. the Cell Above | Decision | Items Found So Far |
| :-: | :-: | :-- | :-- | :-- |
| 1 | `(4, 7)` | `K[4][7] = 9` and `K[3][7] = 9`: **equal** | Item 4 not needed; move up | none |
| 2 | `(3, 7)` | `K[3][7] = 9` and `K[2][7] = 5`: **different** | Item 3 taken; `j = 7 - 4 = 3`; move up | `3` |
| 3 | `(2, 3)` | `K[2][3] = 4` and `K[1][3] = 1`: **different** | Item 2 taken; `j = 3 - 3 = 0`; move up | `3, 2` |
| 4 | `(1, 0)` | `K[1][0] = 0` and `K[0][0] = 0`: **equal** | Item 1 not needed; nothing left to take | `3, 2` = weight `4 + 3 = 7`, value `5 + 4 = 9` |

As a picture, the walk goes like this:

```
start at the answer cell
(4,7) = 9
   |  same as the cell above (3,7) = 9      -> item 4 NOT taken, move up
   v
(3,7) = 9
   |  differs from the cell above (2,7) = 5 -> item 3 TAKEN, room 7 - 4 = 3, move up
   v
(2,3) = 4
   |  differs from the cell above (1,3) = 1 -> item 2 TAKEN, room 3 - 3 = 0, move up
   v
(1,0) = 0
   |  same as the cell above (0,0) = 0      -> item 1 NOT taken
   v
done: items 3 and 2, weight 7, value 9
```

The cells visited are `(4,7)`, `(3,7)`, `(2,3)`, `(1,0)`, which are the bracketed cells in the grid above. Unlike Making Change, **every step moves up one row**, because an item is used at most once.

### 4.7 The Code

```cpp
#include <iostream>
#include <iomanip>
#include <string>
using namespace std;

int K[11][101];   // K[i][j] = best value using the first i items with capacity j

// Builds the table, prints the answer, and returns it.
// Assumes n <= 10 items and capacity <= 100.
int solve(int w[], int v[], int n, int cap, bool showTable) {

    // Row 0 (no items) and column 0 (no capacity): the best value is 0
    for (int j = 0; j <= cap; j++)
        K[0][j] = 0;
    for (int i = 1; i <= n; i++)
        K[i][0] = 0;

    // Fill the table row by row, left to right
    for (int i = 1; i <= n; i++) {
        int wt  = w[i - 1];                      // weight of item i
        int val = v[i - 1];                      // value of item i

        for (int j = 1; j <= cap; j++) {
            K[i][j] = K[i - 1][j];               // option 1: leave item i out

            if (wt <= j && val + K[i - 1][j - wt] > K[i][j])
                K[i][j] = val + K[i - 1][j - wt];  // option 2: put item i in
        }
    }

    // Print the table
    if (showTable) {
        cout << "Table K[i][j] for capacity " << cap << ":" << endl;
        cout << left << setw(16) << "" << right;
        for (int j = 0; j <= cap; j++)
            cout << setw(4) << j;
        cout << endl;

        for (int i = 0; i <= n; i++) {
            string label = (i == 0) ? "no items" : "item " + to_string(i) + " (w=" + to_string(w[i - 1]) + ")";
            cout << left << setw(16) << label << right;
            for (int j = 0; j <= cap; j++)
                cout << setw(4) << K[i][j];
            cout << endl;
        }
    }

    cout << "Capacity " << cap << ": best value = " << K[n][cap] << ", items taken: ";

    // Walk back through the table to find WHICH items were taken
    int j = cap;
    int totalWeight = 0;
    for (int i = n; i >= 1; i--) {
        if (K[i][j] != K[i - 1][j]) {            // the value changed: item i was taken
            cout << i << " ";
            j = j - w[i - 1];                    // less room is left for the other items
            totalWeight = totalWeight + w[i - 1];
        }
    }
    if (K[n][cap] == 0)
        cout << "(none) ";
    cout << "| total weight = " << totalWeight << endl;

    return K[n][cap];
}

int main() {
    // Example 1: the main example
    int w1[] = {1, 3, 4, 5};
    int v1[] = {1, 4, 5, 7};
    solve(w1, v1, 4, 7, true);
    cout << endl;

    // Example 2: another small example
    int w2[] = {2, 3, 4, 5};
    int v2[] = {3, 4, 5, 6};
    solve(w2, v2, 4, 5, true);
    cout << endl;

    // Example 3: nothing fits into the bag
    int w3[] = {4, 5};
    int v3[] = {10, 20};
    solve(w3, v3, 2, 3, true);

    return 0;
}
```

### 4.8 More Examples

**Second example.** Weights `2, 3, 4, 5`, values `3, 4, 5, 6`, capacity `5`. The program's table is:

| `j` | 0 | 1 | 2 | 3 | 4 | 5 |
| :-- | :-: | :-: | :-: | :-: | :-: | :-: |
| **no items** | 0 | 0 | 0 | 0 | 0 | 0 |
| **item 1 (w 2)** | 0 | 0 | 3 | 3 | 3 | 3 |
| **item 2 (w 3)** | 0 | 0 | 3 | 4 | 4 | **7** |
| **item 3 (w 4)** | 0 | 0 | 3 | 4 | 5 | 7 |
| **item 4 (w 5)** | 0 | 0 | 3 | 4 | 5 | 7 |

The answer cell `K[4][5]` is `7`. Walking back: `(4,5)` equals the cell above, so item 4 is not needed; `(3,5)` equals the cell above, so item 3 is not needed; `(2,5) = 7` differs from `(1,5) = 3`, so item 2 is taken and `j = 5 - 3 = 2`; `(1,2) = 3` differs from `(0,2) = 0`, so item 1 is taken. ### 4.9 Greedy Versus DP

Using the running example, here is greedy Rule C (best value per kg) against the best answer for every capacity from 1 to 7. The "Best" column is the last row of the table in Section 4.5:

| Capacity | Greedy Takes | Greedy Value | Best (DP) | Greedy Correct? |
| :-: | :-: | :-: | :-: | :-: |
| 1 | 1 | 1 | 1 | Yes |
| 2 | 1 | 1 | 1 | Yes |
| 3 | 2 | 4 | 4 | Yes |
| 4 | 2, 1 | 5 | 5 | Yes |
| 5 | 4 | 7 | 7 | Yes |
| 6 | 4, 1 | 8 | 8 | Yes |
| **7** | **4, 1** | **8** | **9** | **No** |

Greedy is right for capacities 1 to 6, and goes wrong exactly at the capacity we picked. A method that is wrong for even one input cannot be used when we need the best answer every time. DP is right every time.

### 4.10 Time and Space

Let `n` be the number of items and `W` the capacity.

| Part | Time | Space |
| :-- | :-- | :-- |
| **Filling the table** | `O(n * W)` (each of the `(n+1) * (W+1)` cells takes a constant amount of work) | `O(n * W)` for the table |
| **Finding the items** | `O(n)` (one step for each row) | none extra |
| **Value only, no items** | `O(n * W)` | `O(W)` (one row is enough, see Section 4.11) |

For our example the table has `5 * 8 = 40` cells (28 of them need a calculation, the rest are the zero row and column). That is **not smaller** than the 19 recursive calls or the 16 subsets, because the example is tiny. The picture changes quickly: for 24 items and capacity 24, plain recursion needed 1,961,491 calls but the table has only `25 * 25 = 625` cells. For 100 items and capacity 1000, the table has `101 * 1001 = 101,101` cells, while trying every subset would mean about 1.3 x 10^30 subsets.

The time depends on the **number** `W` itself, not on how many digits it has. A huge capacity makes a huge table. This is called **pseudo-polynomial** time.

### 4.11 Saving Memory -- One Row Instead of a Table

Row `i` of the table is built using **only row `i - 1`**. So if we only need the best value (not the items), we can keep a **single row** `best[j]` and update it in place for each item. There is one rule that must not be broken: **go through `j` from right to left** (from `W` down to the item's weight).

Why? When we update `best[j]`, we read `best[j - wt]`. That cell must still hold the **old** value (without item `i`). Going right to left guarantees this, because the cells to the left have not been changed yet. Going left to right would read cells that already include item `i`, and item `i` would be counted **again and again**. Here is item 2 (weight 3, value 4) being added to the row `0 1 1 1 1 1 1 1`:

```
RIGHT to LEFT  (j = 7, 6, 5, 4, 3)            LEFT to RIGHT  (j = 3, 4, 5, 6, 7)
 j = 6 reads best[3]: still the OLD 1          j = 3 sets best[3] = 4
       -> best[6] = max(1, 4 + 1) = 5          j = 6 reads best[3]: ALREADY the new 4
 (item 2 is used at most once)                       -> best[6] = 4 + 4 = 8
                                               (item 2 is used TWICE: 3 + 3 = 6 kg)
 result: 0 1 1 4 5 5 5 5   (correct)           result: 0 1 1 4 5 5 8 9   (wrong)
```

```cpp
#include <iostream>
#include <iomanip>
#include <string>
using namespace std;

int best[101];   // best[j] = best value for capacity j, using the items handled so far

// backwards = true  -> correct 0/1 knapsack
// backwards = false -> WRONG for 0/1 (an item can be counted again and again)
int knapsack(int w[], int v[], int n, int cap, bool backwards, bool show) {
    for (int j = 0; j <= cap; j++)
        best[j] = 0;

    for (int i = 0; i < n; i++) {
        if (backwards) {
            for (int j = cap; j >= w[i]; j--)               // right to left
                if (best[j - w[i]] + v[i] > best[j])
                    best[j] = best[j - w[i]] + v[i];
        } else {
            for (int j = w[i]; j <= cap; j++)               // left to right
                if (best[j - w[i]] + v[i] > best[j])
                    best[j] = best[j - w[i]] + v[i];
        }

        if (show) {
            cout << left << setw(14) << ("after item " + to_string(i + 1)) << right;
            for (int j = 0; j <= cap; j++)
                cout << setw(3) << best[j];
            cout << endl;
        }
    }
    return best[cap];
}

int main() {
    int w[] = {1, 3, 4, 5};
    int v[] = {1, 4, 5, 7};

    cout << "Capacity 7, one row, right to left:" << endl;
    cout << left << setw(14) << "start" << right;
    for (int j = 0; j <= 7; j++) cout << setw(3) << 0;
    cout << endl;
    int answer = knapsack(w, v, 4, 7, true, true);
    cout << "Best value = " << answer << endl;
    cout << endl;

    cout << "Capacity 10:" << endl;
    cout << "right to left (correct): " << knapsack(w, v, 4, 10, true, false) << endl;
    cout << "left to right (wrong)  : " << knapsack(w, v, 4, 10, false, false) << endl;

    return 0;
}
```

**Verified Output:**
```
Capacity 7, one row, right to left:
start           0  0  0  0  0  0  0  0
after item 1    0  1  1  1  1  1  1  1
after item 2    0  1  1  4  5  5  5  5
after item 3    0  1  1  4  5  6  6  9
after item 4    0  1  1  4  5  7  8  9
Best value = 9

Capacity 10:
right to left (correct): 13
left to right (wrong)  : 14
```

How to read the output:

- **First block:** every printed row is exactly the matching row of the table in Section 4.5 (rows 1 to 4), and the answer is `9`.
- **Second block (capacity 10):** the correct right-to-left loop gives `13` (items 1, 3, and 4: weight `1 + 4 + 5 = 10`, value `1 + 5 + 7 = 13`). The wrong left-to-right loop gives `14`, because it uses item 4 twice (`5 + 5 = 10` kg, value `7 + 7`), which the 0/1 rules do not allow.

> **Important:** in the one-row version, the capacity loop must run from `W` **down** to the item's weight. If the loop is reversed, the program silently solves a **different** problem (items can be reused) and returns a wrong answer.

## 5. Related Problems -- Other Kinds of Knapsack

The three common versions of the problem differ only in what may happen to an item:

| Version | An Item May Be Used | How the Solution Works | Example |
| :-- | :-- | :-- | :-- |
| **0/1 Knapsack** (this note) | **At most once**, whole | Table; "take" reads the row **above**: `val + K[i-1][j-wt]`; one-row loop runs **right to left** | Our running example |
| **Unbounded Knapsack** | **Any number of times**, whole | Table; "take" reads the **same row**: `val + K[i][j-wt]`; one-row loop runs **left to right** | Same idea as the Making Change note, which minimizes the number of coins instead of maximizing a value |
| **Fractional Knapsack** | **In pieces** (can be cut) | No table needed: greedy by value per kg is correct | Section 2.7 |

Another related problem is **Subset Sum**: "is there a set of numbers that adds up to exactly `T`?". It is the 0/1 Knapsack in which every item's value equals its weight.

The only change between 0/1 and Unbounded Knapsack is **which cell the "take" option reads**, and the direction of the capacity loop in the one-row version. Everything else in the table method stays the same.

## 6. Comparing the Approaches

Results for the items `(1,1)`, `(3,4)`, `(4,5)`, `(5,7)` and capacity `7`:

| Aspect | **Greedy** | **Try Every Subset** | **Plain Recursion** | **Dynamic Programming** |
| :-- | :-- | :-- | :-- | :-- |
| **Idea** | Take the best-looking item that fits | Check all `2^n` ways to choose | Try "skip" and "take" for each item | Fill a table once, row by row |
| **Always Correct?** | **No** | Yes | Yes | Yes |
| **Answer for capacity 7** | 8 (items 4, 1), **not the best** | 9 (items 2, 3), 16 subsets | 9, with 19 calls | 9 (items 2, 3), with a 40-cell table |
| **Time** | Very fast | Exponential (`2^n`) | Exponential (about `2^n` calls in the worst case) | `O(n * W)` |
| **Finds Which Items?** | Yes | Yes | Needs extra work | Yes, by walking back through the table |
| **Handles "Nothing Fits"?** | Yes (takes nothing) | Yes | Yes | Yes (the answer cell is `0`) |

## 7. Advantages & Disadvantages

| **Advantages** | **Disadvantages** |
| :-- | :-- |
| **Always gives the best answer** for any set of items, unlike greedy | Needs `O(n * W)` memory for the table (reduced to `O(W)` if only the value is needed) |
| Turns an exponential search into a fast `O(n * W)` solution | Slower than greedy on cases where greedy already works |
| Easy to check by hand, since every cell comes from two cells in the row above | The table grows with the **capacity**: a huge capacity makes a huge table |
| Also tells us **which** items to take, by walking back through the table | The weights and the capacity must be whole numbers |
| The one-row version is only a few lines of code | In the one-row version the loop direction is easy to get wrong |

***

## 8. Summary

| Concept | One-Line Summary |
| :-- | :-- |
| **0/1 Knapsack Problem** | Choose items (each taken whole, at most once) to get the largest total value without passing the weight limit |
| **Running Example** | Items `(w,v)` = `(1,1)`, `(3,4)`, `(4,5)`, `(5,7)` and capacity `7`: the best answer is items 2 and 3, value 9 |
| **Greedy Method** | Take the best-looking item that fits; it gave items 4 and 1 (value 8) here, for every one of the three rules tried |
| **Why Greedy Fails** | It cannot undo its first choice, so a good-looking item can leave a gap that nothing fills well |
| **Recurrence** | `f(0,c) = f(i,0) = 0`; `f(i,c) = f(i-1,c)` if `wi > c`; else `max( f(i-1,c) , vi + f(i-1, c-wi) )` |
| **Plain Recursion** | Correct, but 19 calls for our example and 1,961,491 calls for 24 items, because subproblems repeat |
| **DP Table** | `K[i][j]` = best value using the first `i` items with capacity `j` |
| **Cell Rule** | `K[i][j] = max( K[i-1][j] , val + K[i-1][j-wt] )` when the item fits, otherwise copy the cell above |
| **Base Cases** | `K[0][j] = 0` and `K[i][0] = 0` |
| **Walking Back** | Same as the cell above means the item was not taken; different means it was taken, so reduce `j` by its weight; always move up one row |
| **Always Row Above** | Both options read row `i - 1`, since an item is used only once (Making Change read the same row) |
| **Complexity** | `O(n * W)` time, and `O(n * W)` space (or `O(W)` with one row, filled right to left) |
| **Related Versions** | Unbounded Knapsack reuses items (same row, left to right); Fractional Knapsack allows pieces (greedy works) |
